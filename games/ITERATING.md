# ITERATING.md — how to take the next game iteration (for an OpenCode model)

**Primary iterating model:** `opencode/deepseek-v4.1-flash-free` (fallback: `opencode/mimo-v2.6-flash-free`).
Call pattern on Markus's box: `cd <repo> && opencode run -m opencode/deepseek-v4.1-flash-free "<task>"`
(the generic wrapper `/workspace/dach-jobs/run.sh model promptfile outfile` is for TSV-output jobs; it
requires a tab in stdout, so do not use it for code edits). Keep each prompt to ONE file / ONE change, then
run the checks below yourself. Iteration 1 note: the free-model quota was exhausted at build time, so
iteration 1 code was written by hand; this file is the contract for whichever model iterates next.

## Vision (Markus)
A series of self-made mobile browser games. Every completed level emits a gameplay-data artifact that
seeds the next ITERATION. Human runs outrank sim runs. Only once a game is fun for 5–30 minutes may it start
offering decisions that act as real-world data for other tasks.

## Log schema (gameplay-log v1) — summary
One JSON file per run: `game{id,version,iteration,namespace}`, `run{id,type:human|sim,device,player,seed,tuningSource}`,
`levels[]{level,params,outcome,durationMs,metrics{score,actions,misplays,progress},events[],ext{tetris{lines,pieces,maxHeight,holesEnd,avgHoles,bumpinessEnd,gravityMs,lockDelayMs}}}`,
`transitions[]{from,to,changes[{param,from,to}],mechanicsAdded[],mechanicsRemoved[]}`, `summary`.
Rules: anything tunable goes in `params` (so transitions diff it automatically); game-specific stats go
under `ext.<namespace>`; new mechanics are named in `mechanicsAdded` AND appear as a param (e.g. `garbageRows: 2`).

## Run the sim
```
node games/tetris/sim/run-sim.js                       # all skills, 1 run each, 10 levels
node games/tetris/sim/run-sim.js --skill casual --runs 5 --seed 10 --levels 3
```
Virtual clock: each piece costs bot think time (+150 ms); if think time exceeds fall time the bot panics
(random drop, logged as `misplay` event). Bot durations are FASTER than humans — treat sim duration as a lower bound.

## Read logs and tune
```
node games/tetris/sim/tune.js --dry      # print proposal
node games/tetris/sim/tune.js            # write games/tetris/tuning.json
node games/tetris/sim/tune.js --proxy good
```
**Precedence rule:** per level, if ANY human log (`logs/human/`) contains that level, only human data is used
for it and sim is ignored; otherwise the sim proxy skill (default `casual`) is used. Targets: completion rate
~0.7, level duration 60–300 s. Adjustments: low completion → gravity ×1.15 (and −2 lines if <0.3); high → ×0.9;
too short → +2 lines; too long → −2 lines. The page fetches `tuning.json` at load (falls back to levels.js defaults)
and records `run.tuningSource`.

## Checks before committing
1. `node games/tetris/sim/run-sim.js --runs 2` — good/expert must complete all 10 levels; casual should reach ≥3.
2. Page loads with no JS errors (headless Chrome via CDP, or open locally with `python3 -m http.server`).
3. Validate a log against the schema if a validator is available; at minimum `JSON.parse` + required keys.
4. Bump `ITERATION` (and `GAME_VERSION`) in levels.js for every published iteration.

## Drop-target Tetris (engine param `goal: 'drops'`)
`createGame({ params: { goal: 'drops', dropsTarget: N, ... } })` ends the level after N locked pieces; lines still
score but don't end it (`goal` defaults to `'lines'`, so the 10-level game is unchanged). The combo computes N from the
upcoming Pairwise round:
```
totalWords  = Σ over pairs: words(criterion) + words(A.text) + words(B.text)   (an item shown in two pairs counts twice)
dropsTarget = clamp(round(totalWords / wordsPerDrop), minDrops, maxDrops)
```
Defaults (`games/tetris/tuning.json` → `dropTarget.params`): wordsPerDrop **18**, minDrops 8, maxDrops 60, assumedWpm 225.
Why 18: first human log = 155.8 s / 32 pieces = 4.87 s per piece; 4.87 s × 225 wpm / 60 = 18.3 words. So the Tetris
segment should last about as long as reading the round. test-001: 633 words → **35 drops** (~2.8 min read, ~2.8 min Tetris).
Recalibrate: `node games/tetris/sim/tune.js --drop-target-only` (human logs only). With combo human logs it uses
`totalWords × (tetrisMs/pieces) / pairwiseMs` (the value that would have equalised the two segments), else
ms-per-piece from tetris human logs × assumedWpm. tune.js now also reads `games/tetris/logs/human/` (where the first log lives).

## Logger fix (1.1.0)
The first human log had 32 pieces but 29 `hard_drop` events: `hard_drop` was only logged on hard-drop input, so pieces
that locked by gravity or after soft drop were invisible. Now the engine reports every lock via `onLock` with
`how: hard_drop | soft_drop | gravity | place` (+ pieceNo, pieceType, x, y, rot, linesCleared, holes, maxHeight),
and tetris/combo/sim all log it as a `lock` event, so `count(lock) == pieces`. `hard_drop` events are kept for compat.

## Schema 1.1.0 (additive)
Optional `session {id, kind, segments[]}`; levels can carry `segment`; ext can be written under another namespace
(`ext.tetris`, `ext.pairwise`). Pairwise decisions live in `levels[].ext.pairwise.decisions[]` with pairId, itemA/B,
choice (A|B|tie|not_enough_info, in SET terms even when sides are swapped on screen), winner, strength 1–3, decisionTimeMs,
reasonTags, swapped, undone, source (`human` or `sim:<strategy>`), plus setId/setVersion/demo. See schema/README.md.

## Pairwise sims & aggregation
`node games/tetris/sim/run-sim.js --mode drops --skill casual,good --chooser random,length --runs 2`
→ `logs/sim/combo-*.json` (run.type `sim`). Sim choosers are NOT preferences; they only exercise the pipeline.
`node games/pairwise/tools/aggregate.js` → `games/pairwise/data/scores.human.json` (human logs only; demo sets skipped
unless `--include-demo`). `--sim` → `scores.sim.json` (sim logs only). Output `pairwise-scores` 1.0.0:
`items[]{id, comparisons, wins, ties, losses, winRate, bt, elo}` sorted by Bradley-Terry strength (1 = average).

## Add a new pair set
1. Copy `games/pairwise/sets/test-001.json` to `sets/<setId>.json`; set `setId`, `setVersion`, `demo` (true for fake data).
2. Each pair: `{id, criterion, a:{id,label,text}, b:{id,label,text}}`. Item ids are global: reuse an id to compare the
   same text in several pairs (needed for Bradley-Terry to link items). Keep texts 40–120 words.
3. Play it: `/games/combo/?set=<setId>` or `/games/pairwise/?set=<setId>`; the combo shows words and the drop target.
4. Sim check: `node games/tetris/sim/run-sim.js --mode drops --set games/pairwise/sets/<setId>.json`.
5. Bump `setVersion` whenever any text changes; aggregate with `--set <setId>`.

## Direction change (Markus): tone, not selling copy
Markus's judgement on what *sells* is weak signal; he would rather build tech/UX good enough that content sells itself.
So pairwise now looks for **his personal writing voice**: `sets/tone-001.json` (`kind: 'tone-discovery'`, `demo: false`,
`fictional: true`). Each pair = the SAME fictional message in two tones; criterion "Which sounds more like how you'd want
to write?". Content types: README intro, PR description, LinkedIn shipping post, recruiter reply, commit message, changelog,
tweet about a new skill, onboarding microcopy. Each item has `tone {formality, warmth, brevity, humor, confidence,
technicality, directness, emoji, personal}` in -1..1 (+1 = formal / warm / terse / playful / assertive / technical /
direct / emoji / first person). New choice **'neither'** (both rejected) – excluded from scores, counted in the profile.
Rules for tone sets: no personal data, no real people/companies of Markus's, no theology or nursing content; keep items
short (8–60 words; microcopy is naturally short) so a pick fits a pause. Bump setVersion when texts or tone tags change.

**Tone profile:** `node games/pairwise/tools/aggregate.js` also writes `data/tone-profile.human.json` + `.md` (human logs
only; `--sim` → `tone-profile.sim.*`, labelled SIMULATED). Per dimension: weighted mean of signed wins over comparisons
where the two items differ by ≥0.2 (strength weights 1/1.5/2) with se and n, plus a joint L2 logistic regression beta
(separates confounded dims, but with few logs it can disagree in sign with the mean – trust the mean + confidence).
The `.md` is a style guide a writing model can use directly. Sim persona `persona-terse` (sim-chooser.js) plants a known
taste (brevity + directness, anti emoji/humour) to check the pipeline recovers it.

## Lynx Dash (games/runner/) – runner + tone questions
Original pixel art (Lo the lynx, crows, cacti, coins) drawn in canvas code. Loop: 3-2-1 → **30 s ACTIVE running** (timer
runs only in phase `run`; pause/tab-hide stops it) → one tone question (PairwisePit.mount `single: true`, `round.markShown()`
so decisionTimeMs starts when the question appears) → 3-2-1 → … × `questions` (default 6) → summary (distance, best run,
score, coins, best clean streak, questions, "your tone so far" via RunnerSession.toneMini). Forgiving: 3 lives, shrunk
hitboxes, 1.5 s invulnerability; losing all lives resets run distance and refills lives (round continues). Feel: coyote
100 ms, jump buffer 130 ms, variable jump height, fast-fall when ducking in air. Speed ramps baseSpeed→maxSpeed by
accelPerSec; after each question speed time ×0.8 (`speedKeepAfterQuestion`). Clean segment (0 crashes) → streak, bonus
100 × streak. Inputs: tap/hold canvas or Jump button, swipe down or Duck button, Space/↑/W, ↓/S, P/Esc pause.
Log (`game.id runner`, session kind `runner+pairwise`): levels alternate `segment: runner` (ext.runner: activeMs, jumps,
ducks, crashes, knockouts, nearMisses, coins, distance, maxSpeed, avgSpeed, airMs, clean, streak, cleanBonus, scoreTotal,
lives, speedEnd; events jump/duck/coin/near_miss/crash/knockout/clean_segment/pause) and `segment: pairwise` (ext.pairwise
with one decision). `summary.runner` holds round totals + tone teaser. localStorage `runner.logs.v1` + download button.
Pairs are drawn unseen-first (`runner.seenPairs.v1`). Tuning: `games/runner/tuning.json` (`?q=N` overrides questions).
Sims: `node games/runner/sim/run-sim.js --skill novice,casual,good --chooser random,persona-terse --runs 2` (virtual clock)
and in-page `games/runner/?sim=1&skill=good&chooser=random&fast=16` (bot + chooser, `run.type sim`, SIM badges, localStorage
`runner.simlogs.v1`, exposes `window.__runnerLog`). Headless check: Chrome 390×844, wait for `window.__runnerLog`, expect
12 levels `rprprprprprp`, 6 decisions, no JS errors.
Next: once Markus sends runner logs, tune segment length/speed from crashes per segment and decision times, and add tone-002
pairs targeting the dims with low confidence.

## Shared qualities, profile, recommender (games/shared/)
`qualities.js` (adapters runner | tetris | pairwise, `compute(log)` → `log.qualities`), `qualities.registry.json` (what each game
measures and how), `recommend.js` (+ `RECOMMENDER.md`), `tools/profile.js` → `games/data/player-profile.human.json` (human logs
only). Every game page attaches `qualities` at the end of a run and shows it on its summary; `games/index.html` has
"Which game now?" from localStorage. New game = write an adapter + a registry entry. No clinical language; label rough estimates.

## Roadmap
- **Iteration 1 (done):** 10 levels reachable, L1 = 6 lines (~1–5 min human calibration), logging, sim, tuner.
- **Iteration 2:** ≥2 levels truly tuned from Markus's human logs (run tune.js once logs/human has files);
  compare human vs sim per level and recalibrate bot skill think times to match human durations.
- **Iteration 3+:** new mechanics per level, logged via params + `mechanicsAdded` (garbage rows, hold piece,
  preview count, invisible/flashing pieces, timed goals, combos). Target 5–30 minutes of fun per session.
- **Later:** only when sessions feel fun, add real-world decision hooks (game choices that produce useful data
  for other tasks), then new games in the series reusing logger.js + the schema.
