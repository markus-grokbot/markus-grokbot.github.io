# Ranked game ideas

## 1. Triage Tower

**Core mechanic:** Incoming cards fall into lanes: approve, reject, defer, delegate, or needs-info. Combos reward consistent rapid decisions; special cards force reconsideration.

**Data yielded:**

```js
ext: {
  itemId,
  decision,
  confidence,
  deferReason,
  rationaleTags: [],
  decisionTimeMs,
  changedMind: false,
  suggestedAction
}
```

**Feeds:** Mail triage, job-post filtering, research queues, OpenCode draft review.

**Consumption:** Export decisions as an action queue. High-confidence approve/reject items can be automated; low-confidence or changed-mind items become human-review examples.

**Gimmick risk:** Low. This is almost certainly better as a plain swipe UI for serious work. The game layer may help repetition, but should not obstruct the queue.

---

## 2. Pairwise Pit

**Core mechanic:** Two candidates, drafts, images, videos, prompts, or code patches appear. Pick the better one, optionally predict the margin, then descend to the next matchup.

**Data yielded:**

```js
ext: {
  comparisonId,
  itemA,
  itemB,
  winner,
  criterion: "overall|fit|clarity|style|correctness",
  preferenceStrength: 1|2|3|4|5,
  confidence,
  decisionTimeMs,
  reasonTags: []
}
```

**Feeds:** Best-take selection, CV/cover-letter variants, prompt/skill A/B tests, code-review acceptance.

**Consumption:** Bradley-Terry/Elo-style rankings, judge calibration sets, and training examples for future selection agents.

**Gimmick risk:** Low to medium. Pairwise comparison is naturally game-like, but a swipe-based “A or B?” interface may be equally good.

## 3. Application Draft

**Core mechanic:** Build a job application pack under a time/resource budget. Choose roles, select CV bullets, assemble cover-letter claims, and spend limited “evidence tokens” on tailoring.

**Data yielded:**

```js
ext: {
  roleId,
  selectedClaims: [],
  rejectedClaims: [],
  tailoringChoices: [],
  perceivedFit,
  perceivedInterviewOdds,
  effortBudget,
  confidence,
  tradeoffs: []
}
```

**Feeds:** Job-role ranking and application generation.

**Consumption:** Learn which job attributes the human actually values, which evidence they consider relevant, and where generated packs need review.

**Gimmick risk:** Medium. Useful decisions are real, but the game may trivialize nuanced career choices. Use fictionalized or preprocessed job cards rather than making someone “play” their livelihood.

## 4. Take Selector: Director’s Cut

**Core mechanic:** Watch short clips or inspect thumbnails in a bracket. Pick the best take, identify continuity errors, rate character/music/style fit, and bet confidence before seeing aggregate results.

**Data yielded:**

```js
ext: {
  assetId,
  takeId,
  winner,
  ratings: {
    characterConsistency,
    motionQuality,
    musicFit,
    novelty,
    commercialPotential
  },
  errorTags: [],
  confidence,
  blind: true,
  decisionTimeMs
}
```

**Feeds:** Grok Imagine still/video selection, recurring-character consistency, music-video assembly.

**Consumption:** Build per-project rankings and personal preference profiles. Use disagreements between human and model judges as calibration cases.

**Gimmick risk:** Low. Reviewing media already resembles a game. The main danger is fatigue from watching too many clips.

## 5. Agent Arena

**Core mechanic:** Several hidden agents submit answers, patches, research summaries, or generated assets. The player accepts/rejects, ranks them, and predicts which will survive review.

**Data yielded:**

```js
ext: {
  taskId,
  agentId,
  artifactType,
  decision: "accept|reject|revise",
  ranking,
  defectTags: [],
  confidence,
  predictedOutcome,
  actualOutcome,
  reviewTimeMs
}
```

**Feeds:** OpenCode/local-model review, code demos, prompt/skill evaluation, model selection.

**Consumption:** Track precision of acceptance decisions, agent-specific failure modes, and calibration by task type. Feed accepted/rejected examples into routing rules.

**Gimmick risk:** Medium. The arena framing is fun, but the actual value comes from disciplined review labels. It should support side-by-side diff/video/text views.

## 6. Window Manager

**Core mechanic:** Allocate a limited daily energy/resource bar across Codex, Grok Build, OpenCode, research, and review tasks. New events reveal uncertain future demand.

**Data yielded:**

```js
ext: {
  availableBudget,
  allocations: {
    codex,
    grokBuild,
    opencode,
    research,
    review
  },
  expectedValue,
  urgency,
  uncertainty,
  reallocationEvents: [],
  realizedOutcome
}
```

**Feeds:** Usage-window and budget allocation.

**Consumption:** Compare predicted value against actual completed work, then recommend future allocations.

**Gimmick risk:** High. This may become a spreadsheet with particle effects. Build only if allocation decisions are frequent and consequential.

---

## 7. Calibration Casino

**Core mechanic:** Make predictions before revealing outcomes: “Will this job posting still be open?”, “Will this model answer pass?”, “Will this video judge agree?”, “How many defects will this patch contain?”

**Data yielded:**

```js
ext: {
  predictionId,
  forecast,
  probability,
  confidence,
  resolutionDate,
  outcome,
  scoringRule: "brier|log",
  evidenceTags: []
}
```

**Feeds:** Research digests, job-posting polls, video analysis, reputation scoring, model-judge calibration.

**Consumption:** Maintain calibration curves, Brier scores, and domain-specific confidence adjustments.

**Gimmick risk:** Medium. Betting mechanics can make uncertainty memorable, but they may encourage fake precision. Use probability ranges and explain scoring.

# What to do with Tetris

Keep it, but stop pretending it is the main product.

Tetris is useful as:

- A palette cleanser between review batches.
- An attention and fatigue probe.
- A low-stakes control condition for measuring whether game framing improves later decisions.
- A source of generic interaction data: hesitation, speed, error rate, session abandonment, and recovery after mistakes.

It is not a good source of meaningful task labels by itself. The existing log is valuable infrastructure, but the human signal is currently mostly “can this person tolerate playing Tetris?”

Add an `attention` or `sessionContext` block:

```js
ext: {
  sessionPurpose: "work|palette_cleanser|experiment",
  preSessionEnergy,
  postSessionEnergy,
  perceivedFocus,
  fatigue,
  willingnessToContinue
}
```

Use Tetris as a five-minute break and compare subsequent decision quality against no-break sessions.

# Making sessions more fun and replayable

1. Use short runs with visible endings: 5, 10, or 20 minutes.
2. Give each session a concrete mission: “clear this inbox,” “find three good takes,” “beat the local model.”
3. Add streaks for consistency and calibration, not merely speed.
4. Reveal outcomes later so predictions have delayed payoff.
5. Add progression through unlocked task types, modifiers, and harder ambiguity—not just cosmetic rewards.
6. Allow “one more review” loops with escalating difficulty and a safe quit point.
7. Show useful personal stats: acceptance precision, overconfidence, favorite job attributes, agent blind spots.
8. Preserve human agency: undo, defer, request evidence, and mark “not enough information.” Forced binary choices will poison the data.

# Build first

Build **Triage Tower**, with Pairwise Pit as its second mode.

It has the highest combination of frequency, label value, and implementation simplicity. It can handle mail, job posts, research items, generated media, and code drafts with the same underlying engine.

## Minimal v1

- Mobile card queue.
- Five actions: approve, reject, defer, needs-info, compare.
- One active task type initially: generated-image/video take selection or inbox-like synthetic items.
- Optional confidence: low, medium, high.
- One reason tag.
- Decision time and changed-mind tracking.
- Daily run length: 5 or 10 minutes.
- End screen showing decisions made, deferred items, confidence, and one useful quality metric.
- Export using the existing `gameplay-log v1` plus:

```js
ext: {
  queueId,
  itemId,
  itemType,
  decision,
  confidence,
  reasonTags: [],
  decisionTimeMs,
  changedMind,
  comparisonGroup
}
```

- A simple consumer script that produces:
  - approved/rejected queue,
  - unresolved queue,
  - confidence-vs-outcome report,
  - examples suitable for agent evaluation.

Bluntly: the first product should be a useful decision queue with game mechanics, not a game searching for a use. Tetris can remain the warm-up mode.
